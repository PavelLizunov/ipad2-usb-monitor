# Реализация и подтверждённые ограничения

## Передача и качество

Hyprland создаёт выход `IPAD2`; WayVNC слушает только `10.94.0.1:5904`
на USB Ethernet. iPad использует `10.94.0.2/30`, framebuffer 1024×768×32,
stride 4096 и статический ARMv7-клиент fbvnc.

Адаптивный режим использует стандартные сообщения RFB SetEncodings и
FramebufferUpdateRequest: при движении выбирается Tight/JPEG quality level 6,
после 300 мс без обновлений запрашивается полный кадр без потерь. Следующее
движение возвращает JPEG. Дополнительные запросы учитываются, чтобы не
накапливать очередь. Это убирает постоянные JPEG-артефакты на статичном тексте.
В потоке видео JPEG-компромисс сохраняется, поскольку движения не прекращаются.

Клиент буферизует сокет и использует ARM NEON в JPEG/zlib-ng и преобразовании
RGB→BGRA. На устройстве работает только одно ядро A5. Полноэкранное 60 FPS
в нативном разрешении для любого содержимого пока не подтверждено.

Измерения сделаны по завершённым RFB-обновлениям на одинаковой 14-секундной
анимации testsrc2, источник 60 FPS, пять коротких окон счётчика:

| Режим | Частота |
| --- | --- |
| Исходный нативный ZRLE, потолок 20 | 18.8–20.5 FPS |
| Нативный адаптивный Tight/JPEG | 31.8–40.6 FPS |
| 800×600, JPEG 2, быстрое растягивание | 42.1–51.2 FPS |
| 640×480, JPEG 2, быстрое растягивание | 52.6–60.8 FPS |

Профиль 640×480 визуально оказался неприемлемым для рабочего стола и не
является настройкой по умолчанию. Пользователь потребовал оценивать чёткость
по настоящим снимкам framebuffer: в нативном адаптивном режиме проверенная
статичная область 1024×700 пикселей совпала с источником без отличий.
Краткие окна счётчика иногда показывают чуть больше 60; это не частота панели.
Диагностика времени кадров включается только переменной `K94_VNC_PERF`.

## Поворот и сенсор

Для портретного режима логические размеры виртуального выхода меняются
местами, клиент поворачивает изображение в физический framebuffer.
Это сохраняет соответствие координат мыши. Ручной поворот проверен по снимку
с устройства. Поворот и растягивание выполняются CPU и могут снижать FPS.

Ядро не обнаруживает input-устройств: `/proc/bus/input/devices` и
`/sys/class/input` пусты, `/dev/input` отсутствует. Сенсорный контроллер
планшета не подключён этим портом. Нужны драйвер, описание устройства,
возможно firmware, и затем передача абсолютных координат в Omarchy.
Автоматический поворот по акселерометру не реализован.

## Boot и сохранность состояния

RAM boot работает через активный iOS jailbreak/OpenSSH, kloader, K94 iBSS/iBEC
и подготовленный bundle. Перед отправкой проверяются CPID 8940, BDID 06
и ECID ранее спаренного устройства. Во время USB-переопределения неполные
дескрипторы ожидаются; реальное несовпадение идентичности не пропускается.
Из Recovery можно продолжить по сохранённой идентичности без нового iOS boot.

Постоянная установка Linux не реализована. В подтверждённом запуске mounts
содержали только rootfs, proc/sysfs/devtmpfs/devpts/tmpfs. Накопитель не
монтировался, не прошивался и не стирался. После полного выключения остаётся
требование включить Carbon в iOS и повторить RAM boot.

Для пользователя это конкретный технический предел текущего порта,
а не готовая автономная замена iOS.

## Постоянная интеграция компьютера

Собственные файлы установки:

- `/etc/systemd/network/10-ipad2-k94.link` — имя `ipad2` по MAC gadget.
- `/etc/udev/rules.d/60-ipad2-k94.rules` — доступ к DFU/Recovery и консоли.
- NetworkManager `ipad2-k94-usb` — адрес /30 без default route.
- UFW, если уже активен, — VNC только от iPad на этом интерфейсе.
- Пользовательская служба `ipad2-k94-monitor.service`.
- Отмеченные блоки в пользовательских `monitors.lua` и `bindings.lua`.

Существующие настройки других мониторов и ключи сохраняются.
Репозиторий содержит исходники и производные патчи. Runtime state, ключи,
boot kit, аппаратные идентификаторы и снимки остаются вне Git.
